# D-20260720-01 — Delivery efficiency requires authoritative cold telemetry

Index: [DecisionHistory.md](../DecisionHistory.md)

## Detail

### Objective

Measure how much authoritative model usage and elapsed time are consumed while
delivering a user result, and explain the spend across planning,
implementation, testing, deployment, and reporting. The measurement must make
approaches comparable without incentivizing narrower scope, weaker testing, or
premature completion claims.

### Selected boundary

The policy defines the measurement contract, but it cannot observe provider
counters or runtime intervals by itself. Exact measurement therefore requires
a configured runtime or harness recorder. No such recorder is implemented or
claimed by this policy change. When one is configured, it owns a durable,
concurrency-safe, append-only `EfficiencyLedger.jsonl` outside source worktrees
and routine agent context.

The recorder captures request receipt and first model or tool activity as
separate timestamps, emits start and terminal lifecycle events, and appends
corrections, continuations, later defects, and rework without changing prior
events or double-counting them. It uses authoritative runtime or provider
counters, preserves available provider-native token categories, and uses
monotonic time. Missing coverage remains explicitly unknown; manual estimates
and zero-filled counters are not valid substitutes. Zero is valid only when
complete instrumentation proves no usage.

Each observed span has two independent classifications:

- phase: planning, implementation, testing, deployment, reporting, or
  unattributed;
- activity state: model-active, tool-active, external-wait, user-wait, or
  blocked-wait.

Planning covers requirements, context, research, diagnosis, design, and
sequencing. Implementation covers changes to code, configuration,
documentation, data, and test artifacts. Testing covers executing and reviewing
verification; deployment covers release or environment mutation; reporting
covers user-facing status and handoff. Ambiguous mixed work remains
unattributed.

Measurement provenance remains separate from attribution provenance. Phase,
activity, scope, outcome, verification, task, size, and method classifications
carry runtime-observed, agent-declared, inferred, or unknown provenance and the
classifier or schema version; inferred allocations are never presented as
measured values.

Phase elapsed time is the union of phase intervals and includes waits within
that operation. Activity-state time is reported separately. End-to-end wall
time is not the sum of overlapping agent or phase durations, and summed
per-agent active time is reported as a separate measure. Root and delegated
agents, tool work, retries, failed attempts, rollback, and rework remain in the
same task lineage.

Terminal records bind schema and recorder versions, nonsensitive opaque project
and revision identity, runtime configuration, the agreed requested-scope and
acceptance baseline, user-approved scope changes, requirement coverage,
delivered scope, outcome, verification and evidence provenance, defects and
rework links, counters, coverage, and measurement overhead. Linked later work
uses separate kind and cause dimensions: continuation, retry, rollback, defect
repair, or rework is distinct from agent-caused mistake, changed intent, new
scope, external cause, or unknown. Stable low-cardinality task, scope, and
method tags support compatible comparisons. Prompts, source content, tool
payloads, secrets, credentials, and personal data are excluded.

### Options considered

- A project-root efficiency ledger would be easy to discover, but it would grow
  indefinitely in routine context, mix telemetry with source state, and create
  unnecessary merge pressure.
- Manual phase logging or reconstructed estimates cannot recover authoritative
  provider counters or concurrency-aware intervals and can hide missing
  instrumentation by treating unknown values as precise.
- A runtime-owned cold event stream preserves authoritative provenance,
  lifecycle and concurrency semantics while keeping hot project context small.

### Verification contract

The universal-policy checker must reject missing lifecycle, authoritative
counter, phase/activity separation, concurrency, outcome, privacy, or
anti-gaming requirements. It must also reject additive instructions to estimate
unknown values, store hot project telemetry, rewrite prior events, collapse
dimensions, omit failed work, retain sensitive payloads, or reduce delivery
quality for a better metric.
