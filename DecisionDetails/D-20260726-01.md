# D-20260726-01 — UI implementation audits require an implemented surface

Index: [DecisionHistory.md](../DecisionHistory.md)

## Detail

### Objective

Prevent an implementation audit from starting when the repository contains
only intended UI, evidence, scaffolding, or backend behavior. Keep genuinely
partial product UI eligible so the audit can find its missing screens, states,
wiring, and journeys.

### Selected boundary

The lead first inspects the repository and names at least one repo-owned source
file that implements a substantive target screen, component, or native view.
The builder's `--eligibility-only` preflight and normal queue path both require
recognized executable UI evidence through `--implemented-ui-file`, rather than
trusting the path declaration alone. A qualifying path must be interface
implementation source, not backend code, route or mount scaffolding, a style,
asset, catalog, design-only artifact, prototype, story, test, fixture, example,
or known untouched starter. An inapplicable run exits with code `3` before
creating audit artifacts or workers.

For a real UI toolkit outside the recognizer, the separate
`--implemented-ui-override` form requires an exact UI-specific framework/view
type used in an import, inheritance/conformance, or constructor relationship
and a distinct named screen/component definition whose body uses that type.
Both facts and the relationship are persisted and verifier-rechecked. This
fallback is an explicit human attestation for recall, not a generic path or
two-symbol bypass.

A passed manifest stores the evidence file, qualification method, exact
exception basis when used, and source hash. The verifier reruns the same
qualification and rejects empty source manifests, nonvisual runs, and missing,
empty, duplicate, stale, or hash-mismatched gate evidence. The lead's actual
reasoning effort and runtime provenance remain recorded, but no high-or-higher
minimum is required; the runtime default is sufficient.

### Options considered

- Trigger wording alone is easy to ignore and cannot prevent direct harness
  use or a zero-source manifest from appearing valid.
- Automatic framework or extension detection alone confuses mockups, stories,
  scaffolds, and styles with product implementation and misses uncommon native
  or domain-specific toolkits.
- A lead-inspected path plus positive implementation signals and an exceptional
  exact-source-anchor fallback combines semantic judgment with durable,
  hash-bound enforcement without treating every source file as UI.

### Verification contract

Fixtures must prove that partial web, native, custom-component, server-rendered,
and structurally anchored uncommon-toolkit surfaces qualify, while backend-only
normal or override paths, UI-looking backend strings, imports, empty view
shells, null/route/provider/root-mount scaffolds, missing evidence,
mockup/prototype, story/test, style/asset, placeholder, and untouched-starter
repositories exit as inapplicable without artifacts. The verifier must reject
forged or unrelated source anchors.
A default-effort completed lead must verify, and absent effort provenance must
still fail.
