# D-20260728-01 — User corrections persist in scoped prevention ledgers

Index: [DecisionHistory.md](../DecisionHistory.md)

## Detail

### Context

The user reported repeatedly correcting the same agent mistakes, most often in
UI work but also in other domains. The existing prevention-first policy passed
its checker while requiring no persistent project record of those corrections.
During this change, a first design used one `UserIssueLedger.md`; the user
rejected it as too broad and required separate ledgers for UI, distinct
business-logic perspectives, automation, coding style, and other fields.

### Decision

Each repository may own a `UserIssueLedgers/` tree. It is absent until the first
confirmed user-indicated agent mistake or durable correction. Each Markdown
file owns one narrow surface, domain, or perspective, and business logic may be
split into nested files such as pricing, permissions, or order lifecycle.

Every file contains one title and one five-column table: stable global ID,
bounded applicability, reusable mistake pattern, required behavior, and
prevention/verification. The relative path owns the title and complete ID
namespace, so `BusinessLogic/Pricing.md` maps to `Business logic / pricing` and
`UIL-BUSINESS-LOGIC-PRICING-NNN`; a file cannot conceal mixed scopes behind a
broad name. Rows persist after the immediate fix. A recurrence updates and
strengthens the same row; patterns are not duplicated across files. Agents
inventory the tree before implementation, read every plausibly relevant
ledger, pass applicable IDs to delegated agents, and verify them before
readiness. Cross-cutting work reads every ledger.

### Alternatives considered

- One broad user-issue ledger was initially implemented, but the user rejected
  it because unrelated UI, business, automation, and style lessons would be
  mixed and routinely loaded together.
- `CompletionLedger.md` cannot own these rules because it intentionally deletes
  resolved work; recurring-prevention rules must survive a successful fix.
- `DecisionHistory.md` cannot own every correction because it is a compact
  major-decision index, not a detailed acceptance-rule catalog.
- Regression tests remain necessary but cannot express every cross-cutting
  user preference, rejected interaction pattern, or rule that applies before a
  new test target exists.
- A chronological incident log would preserve evidence but grow noisy and make
  agents reconstruct the operative rule from narratives.

### Enforcement and evidence

The universal policy assigns routing, lifecycle, delegation, and readiness
behavior. The repository checker recursively validates the tree without
following supplied symlinks, binds each path to its title and ID namespace,
requires exact schemas and stable IDs, and rejects empty files, unsafe objects,
duplicate global IDs, duplicate patterns, mixed prose, ambiguous filenames,
generic catch-all leaf scopes, an unsplit business-logic file, and incomplete
traversal. Its self-test includes realistic UI, pricing, and permissions
ledgers, multiple nested business perspectives, mixed catch-all and broad
business-logic must-catch fixtures, related-but-distinct UI patterns, escaped
table characters, invalid structures, cross-file duplicates, symlinked paths,
directory and parent replacement races, a FIFO, and invalid UTF-8.

On 2026-07-28, `python3 scripts/validate.py` passed the complete canonical and
standalone five-skill matrix. Link verification reported all 15 managed skill
installations as direct canonical links across CLI Codex, Claude Code, and the
desktop Codex runtime. Both managed Codex `AGENTS.md` links resolved directly
to the canonical app-wide policy file with identical content.
