# D-20260802-01 — Activation proof is concurrent and target-attributed

Index: [DecisionHistory.md](../DecisionHistory.md)

## Detail

### Evidence and objective

After both Codex hook families were trusted, the recorder proved fresh
task-bound Codex activity but could not attribute it to the two configured
Codex homes. The previous verifier therefore required the user to quit every
client, launch one home at a time, capture a sequence baseline, run a harmless
task, and repeat the process. The user rejected that procedure as poor user
experience and approved a software-owned replacement. Claude activation is not
part of this request and remains Claude's own workflow.

The objective is one bounded verification operation that can distinguish every
selected Codex home while the clients remain open and asks the user only to
create one ordinary fresh task in each instance.

### Selected behavior

- Derive a stable versioned target reference from the existing recorder
  credential, runtime family, and reviewed canonical runtime home. Install only
  that opaque reference in the hook command; never emit or persist the home
  path, friendly label, credential, or derivation input as telemetry.
- Normalize the reference through the recorder's existing one-way identity
  boundary. Store an optional `target_id` alongside the runtime identity and
  propagate it from a task's hook observations into exactly correlated provider
  usage and declarations. Legacy observations remain valid and honestly lack
  per-target proof.
- Keep one recorder, store, schema, installer, and rollback workflow. Do not
  create per-home recorders, ports, ledgers, or mutable target inventories.
- Let the activation helper read an exact digest-approved installation plan,
  capture its own event baseline, and watch all selected Codex targets
  concurrently for bounded time. A target is active only when a fresh task has
  both target-attributed hook lifecycle evidence and correlated provider usage.
- Write detailed target status to a private bounded report outside the source
  worktree. Model-facing output is one concise `REPORT_SAVED` receipt containing
  at least the filename and aggregate active/pending result; it never includes
  paths, target identifiers, raw events, prompts, commands, or payloads.
- Preserve family-level activation evidence for old installations, but report
  per-home attribution as unavailable instead of demanding serial process
  isolation. Codex hook trust remains an explicit host action; no code edits a
  trust store or bypasses the host prompt.
- Keep target-aware activation portable across macOS, Linux, native Windows,
  and WSL with the recorder's existing state separation and safe-file rules.

### Alternatives and boundaries

- Serial process isolation was rejected because it turns recorder verification
  into repeated application shutdowns and manual terminal choreography.
- Friendly names or runtime-home paths in telemetry were rejected because they
  enlarge the privacy surface and become mutable identity.
- A recorder or store per home was rejected because it duplicates lifecycle,
  correlation, locking, and upgrade state without improving the evidence.
- A persisted activation challenge was unnecessary: an agent-owned watch can
  take its own baseline and correlate fresh target-attributed tasks directly.
- Target attribution does not authorize, identify, or authenticate a user. It
  is observational metadata under the confirmed personal, trusted, single-user
  assumptions in `security-assumptions.md`.

This decision refines the fresh-task proof in D-20260801-02 and the shared
recorder architecture in D-20260728-02 without changing their ownership or
security boundaries.
