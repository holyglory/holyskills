# D-20260802-02 — Hook upgrades use a one-shot software handoff

Index: [DecisionHistory.md](../DecisionHistory.md)

## Detail

### Evidence and objective

The reviewed recorder workflow could safely create an immutable plan, but an
agent running inside an affected Codex or Claude host could not remain alive to
apply it after that host exited. The fallback exposed raw apply and verify
commands and made Terminal part of the normal product experience. The user
rejected that interaction and approved a software-owned post-exit handoff.

The objective is a portable installation path in which the agent performs all
technical discovery and orchestration and the user only approves the reviewed
operation, closes and reopens affected hosts once, reviews host hook trust, and
exercises fresh tasks for activation evidence.

### Selected behavior

- Arm one private, bounded worker before shutdown. Bind its immutable request
  to the exact plan ID, digest, transaction identity, affected process
  incarnations, deadline, and one-shot job identity. The arm operation succeeds
  only after the detached worker reports that its request and process watches
  are ready.
- Give the normal handoff a 24-hour default wait and permit an explicitly
  reviewed wait up to seven days. The worker remains one-shot and nonpersistent;
  an OS reboot terminates it and the agent owns any required replan/rearm.
- Wait for the captured process incarnations without signaling or killing
  them. Recheck process identity, cancellation, plan binding, source and target
  drift, and detectable relaunch immediately before mutation. If the gate is
  ambiguous, changed, cancelled, or expired, mutate nothing and save a
  categorical failure receipt.
- Invoke the existing transactional apply and verify implementation. Do not
  duplicate configuration rendering, receiver lifecycle, rollback, or plan
  validation in the worker. A crash or failure remains governed by the durable
  journal and exact rollback/recovery contract.
- Save a canonical private bounded receipt outside routine context. Its public
  output names the saved file and exposes only categorical status and bounded
  counts; it excludes credentials, paths, commands, process identities, raw
  exceptions, telemetry, prompts, payloads, and user content.
- After a reboot or other transaction-identity conflict, permit read-only
  status to return only a canonical exact job-and-plan-digest-bound receipt
  that strictly proves mutation never started and claims no success. Never use
  this recovery observation to authorize apply, trust review, activation,
  rollback, or successful verification.
- Use a version-neutral launcher at the stable per-user state path in Codex and
  Claude hook commands. The launcher strictly validates settings and the
  versioned immutable target before dispatch. Migration from older versioned
  hook paths happens once; later compatible upgrades leave host hook commands
  unchanged.
- Preserve the existing loopback port and credential when the installed
  receiver supports authenticated retirement and neither credential nor
  security posture changes. Retain fail-closed rotation and conflict behavior
  for legacy or explicitly changed ownership boundaries.
- Keep raw plan/apply/verify/rollback commands documented only as agent-owned
  recovery operations. Never bypass Codex hook trust or claim that a healthy
  recorder grants task authority.

### Security and portability boundary

This is a same-user, local-only, non-privileged background operation under the
confirmed assumptions in `security-assumptions.md`. It introduces no daemon,
remote service, administrator boundary, new credential, or trust bypass. It
uses argv-only detached launch, a minimal environment, private state, bounded
waiting, exact process-incarnation evidence, and no process termination.

The implementation supports macOS, Linux, native Windows, and WSL. Native
execution evidence remains distinct from implemented behavior, and actual
deployment on a newly introduced platform still triggers the smallest relevant
assumption review. No portable process API can prevent a user from launching a
new host after the final check; the workflow therefore asks the user not to
reopen until the saved terminal receipt and fails closed on detectable races.

### Alternatives and boundaries

- Manual Terminal commands were rejected as a normal interface because they
  shift deterministic orchestration and error handling onto the user.
- A permanent daemon, privileged helper, scheduler task, login item, or remote
  installer was rejected because a one-shot same-user worker is sufficient.
- A 15-minute normal deadline was rejected after the live handoff expired before
  the next resume. An unbounded or reboot-persistent worker remains rejected;
  delayed-return tolerance and agent-owned rearm preserve the one-shot boundary.
- Applying while affected hosts remain active was rejected because it weakens
  restart and activation evidence and can leave a host using stale settings.
- Changing the host trust store was rejected; explicit hook review remains a
  host-owned gate.
- Endpoint and credential rotation on every version was rejected because it
  creates unrelated configuration churn without a changed security assumption.

This decision refines D-20260801-02 and D-20260802-01 without changing the
recorder's canonical ownership, privacy schema, or activation-proof boundary.
