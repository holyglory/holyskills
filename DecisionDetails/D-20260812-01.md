# D-20260812-01 — Efficiency evidence is persistent, phase-attributed, and optionally projected

Index: [DecisionHistory.md](../DecisionHistory.md)

## Detail

The delivery-efficiency recorder remains the per-account authority and stores
its append-only event ledger outside source worktrees. A task start may bind a
repository only by hashing a transiently discovered worktree root with the
installation-local secret; durable events, reports, exports, and UI projections
never contain a repository path.

The private authoritative store separately keeps an integrity-protected,
bounded repository basename for local display. Standalone `report --tasks` and
`report --repositories` use that label plus chronological task ordinals, so
readings remain understandable when no Coordinator is installed. These labels
never enter the cold event ledger or optional Coordinator projection.

Persistent activation is derived from verified history under the current
target identity. A fresh watch remains useful for installer diagnostics, but a
timeout or expiry is not recorder state and cannot deactivate a previously
proven target.

Agents declare meaningful phase boundaries through the exact stable launcher.
Declarations are balanced and non-overlapping. Authoritative usage observed
while exactly one valid phase is open inherits that phase with
agent-declared attribution provenance; ambiguous or out-of-phase usage remains
unattributed rather than estimated.

For managed Codex targets, the hook may read the exact host-supplied rollout
path only after proving it is a regular non-symlinked `rollout-*.jsonl` beneath
that target's recorded Codex home. It parses only task boundaries and
provider-native token counters, discards every content-bearing record, binds
the counters to the exact session and turn, and deduplicates them against an
exporter source. The runtime Stop boundary captures final-response usage and
closes the one open reporting phase after that usage is stored.

Repository reports retain provider-native token categories, exact known sums,
coverage, outcomes, timing, and bounded tool/phase classifications. A repeated
work pattern becomes an automation-review candidate only after at least three
comparable non-automated terminal tasks; the candidate is evidence for review,
not a mandate to automate.

When a local operations coordinator advertises the compatible versioned ingest
capability, a terminal declaration may publish one bounded cumulative snapshot
for the current opaque repository. Export failure never blocks recording or
delivery. The coordinator stores independent per-account snapshots and the UI
merges them by repository while preserving unknown coverage and separate token
categories. Without that capability the recorder, local labels, task and
repository reports, token attribution, and automation-candidate analysis all
work normally; only the optional shared UI surface is absent.
