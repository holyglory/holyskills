# D-20260819-01 — Complete agreed scope does not authorize invented scope

Index: [DecisionHistory.md](../DecisionHistory.md)

## Detail

### Evidence and objective

The user clarified that the strong rule against under-engineering was meant to
prevent agents from simplifying requested work for speed, leaving temporary
plumbing behind, or displaying made-up UI numbers, parameters, and results that
never receive a real implementation. It was not permission to invent adjacent
product requirements.

The reported failure was the opposite kind of incompleteness: a request for
Google OAuth and invitation-based access grew into encryption and preservation
behavior for a hypothetical expired-invitation recovery case. That behavior may
be reasonable after an informed choice, but the request, accepted scope, and
confirmed assumptions had not selected it. The active policy allowed this drift
because its August materiality threshold gated only larger expansions, and the
phrase "credible project need" did not require evidence.

The user also reported that completion ledgers contained enough implementation
jargon to hide the product direction, current user impact, and next meaningful
result even when their table fields were technically populated.

### Selected behavior

- Complete every explicit requirement, accepted detail, visible promise,
  exposed value, and necessary supporting behavior end to end. If any remains
  incomplete, record that exact gap immediately; no agreed detail is too small
  for the active completion ledger.
- Define in-scope work from the request, acceptance criteria, recorded
  decisions, user-confirmed assumptions, current-system evidence, and the
  minimum implementation necessary for the requested behavior to work end to
  end. A possible edge case or generic best practice is not evidence by itself.
- Before implementing any agent-proposed addition outside that boundary,
  explain the proposal and recommendation and obtain explicit user approval.
  This applies even to small additions. It includes new product behavior,
  recovery or preservation policies, data lifecycle, controls, UI states,
  dependencies, infrastructure, and continuing maintenance.
- Do not interrupt the user for an optional idea the agent notices and declines
  to implement. Routine low-level implementation choices and reviewed tools
  that preserve established scope remain direct. Questions about materially
  distinct ways to fulfill agreed work still use the proportional decision
  threshold from D-20260801-03.
- Make every completion-ledger row readable without implementation knowledge.
  Lead with the incomplete outcome, user or product impact, readiness effect,
  current blocker or next result, and observable closing proof. Paths,
  identifiers, and test names may follow as supporting detail; raw logs remain
  external artifacts.
- Production UI never uses plausible invented values to conceal missing data,
  processing, or persistence. It shows an honest unavailable state and tracks
  the agreed integration until it works.

### Alternatives and boundaries

- Keeping the material-only expansion gate was rejected because a series of
  individually small additions can still change the product, maintenance
  burden, and delivery direction without consent.
- Restoring an interview for every possible improvement was rejected because
  merely noticing and declining an idea changes no work. Approval is required
  when the agent actually proposes to implement scope outside the
  evidence-backed boundary.
- Requiring approval for every internal coding decision was rejected. The
  minimum production-grade implementation of agreed behavior is already
  authorized unless it introduces a materially distinct in-scope choice or a
  new product, data, control, operational, or maintenance commitment.
- Removing technical detail from the completion ledger was rejected. Technical
  evidence remains useful after a plain-language outcome and impact; it must
  not replace them.
- Synthetic fixtures, design examples, and explicitly declared mock-data
  prototypes remain valid within their stated non-production boundary. They
  cannot support a production-completion claim.

### Durable prevention and verification

`UIL-AGENT-WORKFLOW-005` now distinguishes full implementation from invented
scope, `UIL-AGENT-WORKFLOW-014` owns reader-first incomplete-work reporting, and
`UIL-UI-003` owns truthful data-backed UI content. The universal-policy checker
requires those contracts. Its recall fixtures cover small unrequested edge-case
work, imagined needs, omitted small gaps, technical-only ledger prose, and
invented production values. Its precision fixtures preserve necessary in-scope
implementation, declined optional ideas, useful technical detail after plain
language, honest unavailable states, and declared prototypes.
