# D-20260819-02 — Product delivery uses a permanent software-owned ledger

Index: [DecisionHistory.md](../DecisionHistory.md)

## Detail

### User-confirmed direction

The user requested one skill that combines product and project delivery for a
repository. It gathers requirements, creates release scopes and implementation
plans, coordinates execution tasks, decides whether worker proposals are
clarifications or drift, controls incomplete-work state, prevents silent
blockage, and reports in the language of user requirements.

The coordinator is not read-only. Its ordinary topology is one coordinator
task and one primary execution task; that executor may use Ultra and spawn its
own subagents. The skill has no separately advertised direct-execution mode.
The coordinator may explain and recommend a response to true product expansion
but cannot approve it for the user.

The work graph is authoritative in a database. Every task has evidence-based
completion from 0 through 100 and a release contribution weight. Release and
overall progress are software-calculated weighted values, while readiness
remains a separate gate.

The Completion Ledger is also software-owned database state. It records real
unfinished or compromised behavior introduced or detected at any time,
including missing downstream behavior, absent data or integrations, stubs,
placeholders, temporary wiring, incomplete verification, and materially
suboptimal temporary solutions. Issues are never deleted. Implementation,
verification, reopening, release moves, decisions, and evidence append to the
permanent story. Routine agent queries return not-implemented work; one issue's
history is loaded only when needed.

Monitoring consumes rare milestone, blocker, scope, issue, evidence, failure,
and completion events. While execution remains active, the coordinator also
performs one compact hourly reconciliation of task state, database state,
expected updates, blockers, failures, and scope revision. Raw executor or
subagent output does not enter coordinator context.

## Implementation boundary

The seventh skill owns a portable transactional SQLite state engine with
release, requirement, task, dependency, completion issue, immutable event,
progress, monitoring, and renderer-neutral Gantt data surfaces. The database is
bound to the Git common-directory identity so linked worktrees share state; an
explicit absolute database path is available for a project-established
backend location.

Holy Skills does not regain ownership of the independently versioned
DevCoordinator, its applications, or its source. The skill may use a separately
installed DevCoordinator for Gantt rendering only after capability discovery
advertises a compatible action. The installed capability observed during this
change did not advertise delivery-graph or Gantt actions, so no unsupported
command, checkout dependency, or completion claim was introduced.

## Policy reconciliation

D-20260714-02 selected an open-only `CompletionLedger.md` because routine
context should not grow with resolved rows and Git already retained history.
The new database requirement supplies the explicit audit-retention need named
by that decision's revisit condition without reintroducing history into routine
model context. Universal policy therefore keeps the Markdown file as the
default active-only mode and permits exactly one recorded software-owned
database mode with permanent events, bounded active queries, and no parallel
file ledger.

## Verification expectation

The skill's deterministic self-test must prove database initialization,
repository binding, acyclic dependencies, weighted progress, evidence-gated
task completion, blocking-issue enforcement before and after implementation,
permanent issue history, deletion rejection, premature-release rejection,
stale-work detection, scope revision, compact work orders, and Gantt data. The
repository gate must recognize seven canonical skills, run the new self-test in
place and from a standalone copy, compile its Python, validate the universal
policy alternative, and preserve the independent-repository boundary.
