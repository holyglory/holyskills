# D-20260820-02 — Ongoing coordination requires verified scheduling

Index: [DecisionHistory.md](../DecisionHistory.md)

## Detail

### Reported failure

The user observed that `coordinate-product-delivery` messaged its primary
execution task one or a few times and then stopped. It neither continued
polling nor guided stale, failed, blocked, or drifting work. The coordinator had
sent a final response, ending the active run that its fallback depended on.

The defect was reproduced in the skill contract: scheduled support was
optional, active-turn hourly reconciliation was accepted when scheduling was
unavailable, and no readiness gate prevented a success handoff without a
schedule or first run. The database made state durable but did not create a
future wake-up.

### Authoritative product behavior

Official OpenAI scheduled-task documentation states that scheduled tasks can
run in the background, a scheduled task inside an existing chat returns to that
chat with its context, minute-based intervals support active follow-up loops,
and such tasks can poll long-running operations. It also states that local
project tasks require the desktop app running, the computer on, and the project
available on disk.

The coordinator therefore cannot claim ongoing monitoring until it has:

1. Created and enabled an hourly scheduled task inside the same coordinator
   chat, not a standalone run.
2. Stored coordinator, executor thread, executor host, automation, release, and
   scope identities.
3. Stored a retained cursor, stable run-key rule, overlap behavior, next run,
   and local-runtime availability state.
4. Completed and verified an immediate first scheduled reconciliation.
5. Reported the schedule ID, cadence, next run, executor identity, and first-run
   evidence before ending the initial turn.

Missing automation capability, a wrong destination, failed creation, failed
first run, or unavailable local runtime leaves monitoring unarmed and blocked.
The coordinator records that state, asks the user to enable or manually create
the same-chat schedule, and never falls back silently to active-turn polling.

### Software enforcement

The product-delivery database stores monitoring configuration and permanent run
history. State progresses through `unarmed`, `arming`, `armed`, `blocked`, and
`stopped`. Each invocation claims an idempotent run key; exact replay returns
the prior state and overlapping work records `skipped_overlap`. Successful runs
persist the cursor and next run; failures block monitoring. Releases cannot
transition to released, paused, or cancelled while their automation remains
enabled.

### Verification expectation

Skill fixtures must catch optional scheduling, active-turn fallback,
independent scheduled runs, missing thread/host IDs, missing cursor, overlap,
missing first-run evidence, missing local-runtime availability, and absent stop
behavior. Database tests exercise unarmed, arming, armed, blocked, overlap,
idempotent replay, cursor retention, release-transition refusal, and verified
stop. Host integration is not armed when the automation-management tool is not
available; that limitation remains explicit rather than simulated.
