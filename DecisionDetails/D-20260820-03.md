# D-20260820-03 — Recorder availability requires host-loopback proof

Index: [DecisionHistory.md](../DecisionHistory.md)

## Detail

### Observed failure and correction

Agent-issued recorder status, report, phase, and terminal commands were run
inside a network-restricted coding sandbox. They returned
`receiver-unavailable`, `StorageUnavailableError`, or
`RuntimeConfigurationError`, and the agent incorrectly reported that repository
and chat token statistics were unavailable.

Read-only host inspection proved a listener on configured loopback port 58547,
owned by a detached `/usr/bin/python3.13` receiver running since 2026-08-13.
An authenticated bounded health request using the current settings returned
HTTP 200, recorder 0.2.8, and the expected token identity. Repeating the exact
installed launcher through the approved host boundary returned:

- receiver healthy;
- store healthy with valid ledger integrity and no pending recovery;
- schema 1.2;
- 33,562 events after a balanced declaration proof;
- successful task and repository reports.

The Codex OTel endpoint and credential match current recorder settings. All
eight lifecycle hooks reference the version-neutral stable launcher, and each
has host trust state. The original errors therefore described sandbox network
isolation, not recorder downtime.

### Remaining coverage gaps

The repository report is available but partial. Many historical tasks lack
terminal and phase attribution because their agent declarations failed at the
sandbox boundary; exact missing history cannot be reconstructed. Future
declarations now use the approved host boundary.

Installed recorder 0.2.8 remains healthy. Canonical 0.2.9 was planned with the
required credential rotation but its deferred job failed before mutation with
`managed-daemon-exit-timeout`, leaving 0.2.8 safely active. The corrected 0.2.9
source and realistic managed-helper tests pass, but deployment still requires a
new reviewed plan, a client close/reopen boundary, and fresh task proof.

Only `holygloryTT` currently has an account-local recorder. `holyglory`, `axel`,
and `slawa` have the skills but no recorder state or launcher. Because account
credentials, hooks, receiver processes, and raw event stores remain separate,
complete four-account coverage requires an explicit first installation and
fresh task proof in each account. DevCoordinator may aggregate only the bounded
opaque repository projection.

### Permanent availability contract

1. Hooks and OTel continue using the stable state launcher and lazily restart
   the detached receiver after process loss.
2. Sandboxed agents run only exact stable recorder commands through the narrow
   approved host boundary; one denied call never establishes health.
3. Each task records balanced phases and a terminal declaration while its
   authoritative binding is live.
4. Reports use recorder 0.2.9 task and repository views after the reviewed
   upgrade; unknown historical categories remain unknown.
5. Each user-owned OS account receives its own installed and activated recorder
   before its chats are described as covered.
