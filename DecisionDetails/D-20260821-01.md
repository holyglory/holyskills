# D-20260821-01 — Approval is one plain-language outcome decision

Index: [DecisionHistory.md](../DecisionHistory.md)

## Detail

### Evidence and objective

The user reported that agents repeatedly stopped for approvals framed around
implementation details the user did not understand. Questions arrived one at a
time as new mechanics were discovered, and some required the user to repeat an
internal identifier, digest, command, or exact confirmation phrase.

Earlier policy established when a decision was material and required approval
for agent-proposed scope additions. It did not define approval as consent to an
understandable outcome and its boundaries, nor did it make the agent responsible
for finishing read-only discovery and consolidating the consequences first.

### Selected behavior

- Complete all available read-only investigation before asking an approval or
  other blocking question.
- Bundle all known consequential effects into one decision. Do not request
  serial approvals as implementation details emerge.
- Lead with a plain-language explanation of the problem, recommended outcome,
  boundaries, what will and will not change, user-visible or operational
  consequences, meaningful tradeoffs, and why the decision is needed.
- Treat a plain yes as approval of the recorded outcome and boundaries. The
  user is not approving only the technical steps named in the message.
- Never require the user to repeat or transcribe an internal identifier,
  digest, command, confirmation string, or technical incantation.
- When a host or tool has a mandatory native approval surface, invoke it
  directly after the plain-language explanation. Do not relay its internal data
  through chat.
- Continue autonomously through implementation details inside the approved
  boundaries. Ask again only if later evidence materially changes the outcome
  or boundaries, then present one updated bundled decision.

### Alternatives and boundaries

- Removing approval gates was rejected because the user still owns product
  scope, consequential mutations, and other materially distinct outcomes.
- Approval for every implementation step was rejected because it transfers
  technical discovery to the user and fragments one decision into noise.
- A technical summary followed by a yes/no prompt was rejected when the summary
  does not first explain the actual problem, outcome, and boundaries.
- Native host or tool controls remain in force when mandatory. The agent uses
  them directly; this decision removes chat transcription, not platform safety.
- A genuinely changed outcome or boundary is a new decision. Newly discovered
  mechanics inside the approved plan are not.

### Durable prevention and verification

`UIL-AGENT-WORKFLOW-015` owns the recurring mistake. The universal-policy
checker requires the investigation, bundling, plain-language, approval-scope,
plain-yes, direct-native-control, and updated-plan contracts. Its self-test
rejects early, piecemeal, technical-only, mechanics-only, identifier-copy, and
prescribed-phrase approval requests while preserving valid bundled decisions,
technical appendices, native controls, and materially changed plans.
