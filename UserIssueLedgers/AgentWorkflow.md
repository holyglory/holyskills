# User Issue Ledger: Agent workflow

| ID | Applies to | Mistake pattern | Required behavior | Prevention and verification |
| --- | --- | --- | --- | --- |
| UIL-AGENT-WORKFLOW-001 | Planning and implementation in every repository | Reusable user-indicated mistakes were handled only in the current task and could recur in later work. | Preserve each confirmed pattern in its narrowly scoped project ledger and apply every relevant row before implementation. | Enforce the universal policy contract, realistic policy-checker fixtures, and recursive scoped-ledger validation. |
| UIL-AGENT-WORKFLOW-002 | Designing or extending user-issue ledgers | Unrelated UI, business, automation, or coding corrections were combined in one broad ledger, obscuring which rules applied. | Keep one path-bound ledger per surface or bounded business perspective; never revive a single catch-all file. | Bind every ledger path to its title and ID namespace, and test rejection of a mixed-scope file plus acceptance of multiple nested business perspectives. |
| UIL-AGENT-WORKFLOW-003 | Runtime-injected context and agent startup messages | Authentication or telemetry activation was presented as if it authorized the agent to act. | Treat sign-in and recorder state as operational facts only; never claim or imply authority beyond the user's request. | Require startup context to state that it grants no additional permission, reject positive authorization wording in regression tests, and distinguish authentication from authorization in the handoff. |
| UIL-AGENT-WORKFLOW-004 | Full test, debug, audit, migration-rehearsal, and deployment cycles | Agents stopped at each non-critical gap, fixed it, and restarted the full cycle, losing later failure evidence and repeating expensive setup. | Finish the current cycle after non-critical failures, record all actionable gaps concisely, batch related fixes after the pass, and then rerun the complete relevant cycle. Stop early only when continuation risks harm, corrupts shared state, destroys evidence, or makes later results invalid. | Add policy and checker fixtures for finish-pass-then-batch-fix behavior; make multi-check runners and ad-hoc independent diagnostic command groups collect every exit status instead of short-circuiting with fail-fast chaining; verify a usable test deployment may proceed with disclosed gaps while readiness remains incomplete. |
| UIL-AGENT-WORKFLOW-005 | Engineering scope and risk controls | A preference against under-engineering either disappeared from policy, expanded into unrequested migrations, preservation, hardening, or infrastructure, or forced an exhaustive interview for a routine skill or tool invocation whose established scope and controls were already known. | Under-engineering the agreed result is unacceptable and implementation gaps are more serious than reasonable over-engineering. Ask for explicit approval before a material expansion beyond the requested result or credible project need only when an unresolved answer could plausibly change scope, controls, cost, complexity, maintenance, reversibility, or risk enough to cause meaningful rework or over-engineering. Use existing confirmed context and read-only discovery first. Keep the question concise and proportional by default; include only the decision details needed for an informed answer, expanding the explanation with the decision's impact. A routine invocation of one reviewed skill or tool that preserves established scope and posture does not trigger an expansion interview. | Require the asymmetry, material-impact threshold, proportional-question contract, and routine-invocation false-positive guard in universal policy; add positive, missing-threshold, overbroad-question, and contradiction fixtures; reject automatic hypothetical hardening, disposable-test-data preservation, and silent material scope expansion. |
| UIL-AGENT-WORKFLOW-006 | Agent-controlled context, tool selection, and tool output | Agents repeatedly loaded broad unchanged rules, unrelated skills or tools, oversized file ranges, raw logs, full audit reports, or unchanged images, causing high token use without improving the result. | Load only context and capabilities relevant to the current task, use targeted reads and bounded software-generated receipts, keep complete raw evidence and audit results in cold artifacts, and do not reload unchanged content already available in the live context. Every artifact receipt must identify at least the saved filename. | Measure canonical policy size and startup catalogs, add policy checks for relevance and bounded output, require filename-bearing artifact receipts, and distinguish host-injected overhead from repository-controlled behavior. |
| UIL-AGENT-WORKFLOW-007 | Cross-runtime subagent effort selection | Agent workflows named only an internal effort value, obscuring that the runtime UI exposed the same setting under a different label and risking inherited high-effort context. | Name both values—Codex selector `Light`, runtime `low`—validate the selected runtime/model, and use an isolated worker context; if runtime `low` is genuinely unsupported, use the workflow's disclosed manual fallback instead of an invalid spawn or inherited parent transcript. | Require context-light forks with complete prompts, exact label/value wording, filename-bearing artifact-first worker receipts, and fixtures that reject missing mappings or inherited-context instructions. |
| UIL-AGENT-WORKFLOW-008 | Heavy repository-audit skill activation | Full-repository implementation, test-coverage, and implemented-UI audits could enter context through broad implicit matching even when the user had not deliberately requested their expensive exhaustive workflows. | `full-repo-audit`, `full-repo-test-coverage-audit`, and `ui-implementation-audit` require deliberate direct skill invocation; ordinary implementation, UI work, review, testing, visual checking, or gap-finding requests must not activate them implicitly. For `ui-implementation-audit`, the explicit commands are `$ui-implementation-audit` in Codex and `/ui-implementation-audit` in Claude Code. | Set `policy.allow_implicit_invocation: false` in all three Codex metadata files; set Claude Code's native `disable-model-invocation: true` for the scoped `ui-implementation-audit` correction; state the explicit-only gate in its skill contract; and validate both native gates plus the explicit Codex entry prompt. |
| UIL-AGENT-WORKFLOW-009 | Deterministic audit and verifier CLIs | Context isolation depended on the agent remembering an optional quiet/receipt flag, so a valid invocation could still print a complete audit report into model context. | Software owns artifact creation and context-safe output: a normal agent-facing verifier invocation writes complete results to deterministic files and emits only a bounded receipt naming those files; printing a full report requires an explicit human-only opt-in. | Exercise clean, finding, coverage-failure, and setup-failure paths; prove artifacts contain full evidence, default stdout is one bounded receipt, and only the explicit human-output flag prints the report. |
| UIL-AGENT-WORKFLOW-010 | Multi-instance hook installation, activation, and verification | The workflow first required serial client isolation and manual sequence commands, then exposed digest-bound apply/verify commands in Terminal; its first software handoff also used a hidden 15-minute deadline and could not report a saved no-mutation failure after a reboot changed volatile filesystem device identity. | Give each reviewed Codex home privacy-safe opaque attribution; let one agent-owned concurrent watch capture its own baseline; and let a recorder-owned one-shot handoff apply and verify the exact reviewed plan after affected processes exit. The bounded wait must cover a realistic delayed user return, and a strict no-mutation failure receipt must remain reportable after host restart without authorizing apply or success. Normal users should only approve the reviewed operation, restart affected hosts once, approve host trust, and exercise one fresh task in each instance. Terminal commands are recovery-only; a rebooted or expired handoff is replanned and re-armed by the agent. | Prove independent interleaved target correlation plus a detached, bounded, plan/digest-bound handoff on macOS, Linux, native Windows, and WSL; test realistic delayed return, process identity, exit waiting, PID reuse/relaunch, reboot-time identity drift, strict failure-only status recovery, drift, timeout, crash, collision, rollback, receipt privacy, and unrelated-process preservation; require private filename-bearing receipts and keep manual commands explicitly outside the normal path. |
| UIL-AGENT-WORKFLOW-011 | `user-journey-docs-audit` activation | A greenfield request to critique a domain idea, discuss requirements, and write a specification was treated as a request to audit an existing documentation set because both tasks mentioned product intent, UI, and pre-implementation decisions. | Invoke the skill only when existing product or journey documentation is the audit target and the user requests a documentation-completeness or UI-readiness assessment. Do not activate it for brainstorming, domain or data modeling, database/system specification, ordinary requirements discussion, or co-writing a new specification; “do not start coding,” “critique,” and “roast” are not audit signals by themselves. | Put the complete positive and negative trigger boundary in selector-visible frontmatter, stop before inventory or interview when the applicability gate fails, mirror the boundary in user-facing metadata and README guidance, and test realistic must-call and must-not-call prompts including the reported numbering-system request. |
| UIL-AGENT-WORKFLOW-012 | In-scope local preview, browser QA, and development-runtime coordination in any repository | Agents repeatedly asked for explicit chat authorization before using Playwright or the configured DevCoordinator even though the user wanted those routine tools used autonomously, delaying implementation and verification. | Treat the user's instruction as standing permission to invoke browser automation directly and use the configured development coordinator for in-scope local runtime work in any repository without a separate chat approval. The permission does not expand scope or authorize destructive, production, credential, trust-bypass, or otherwise separately gated actions. | Require the standing-permission boundary in universal policy; reject direct permission questions, stated approval needs, target-first prompts, and ask-before-use phrasing for both tool families; preserve false-positive guards for material scope expansion, production mutation, destructive work, credentials, security gates, installation, and host-owned approval prompts. |
