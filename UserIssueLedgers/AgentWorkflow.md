# User Issue Ledger: Agent workflow

| ID | Applies to | Mistake pattern | Required behavior | Prevention and verification |
| --- | --- | --- | --- | --- |
| UIL-AGENT-WORKFLOW-001 | Planning and implementation in every repository | Reusable user-indicated mistakes were handled only in the current task and could recur in later work. | Preserve each confirmed pattern in its narrowly scoped project ledger and apply every relevant row before implementation. | Enforce the universal policy contract, realistic policy-checker fixtures, and recursive scoped-ledger validation. |
| UIL-AGENT-WORKFLOW-002 | Designing or extending user-issue ledgers | Unrelated UI, business, automation, or coding corrections were combined in one broad ledger, obscuring which rules applied. | Keep one path-bound ledger per surface or bounded business perspective; never revive a single catch-all file. | Bind every ledger path to its title and ID namespace, and test rejection of a mixed-scope file plus acceptance of multiple nested business perspectives. |
| UIL-AGENT-WORKFLOW-003 | Runtime-injected context and agent startup messages | Authentication or telemetry activation was presented as if it authorized the agent to act. | Treat sign-in and recorder state as operational facts only; never claim or imply authority beyond the user's request. | Require startup context to state that it grants no additional permission, reject positive authorization wording in regression tests, and distinguish authentication from authorization in the handoff. |
| UIL-AGENT-WORKFLOW-004 | Full test, debug, audit, migration-rehearsal, and deployment cycles | Agents stopped at each non-critical gap, fixed it, and restarted the full cycle, losing later failure evidence and repeating expensive setup. | Finish the current cycle after non-critical failures, record all actionable gaps concisely, batch related fixes after the pass, and then rerun the complete relevant cycle. Stop early only when continuation risks harm, corrupts shared state, destroys evidence, or makes later results invalid. | Add policy and checker fixtures for finish-pass-then-batch-fix behavior; make multi-check runners and ad-hoc independent diagnostic command groups collect every exit status instead of short-circuiting with fail-fast chaining; verify a usable test deployment may proceed with disclosed gaps while readiness remains incomplete. |
| UIL-AGENT-WORKFLOW-005 | Engineering scope and risk controls | Agents either reduced the agreed result for speed, or treated an imagined edge case as a credible project need and silently added unrequested recovery, preservation, encryption, migration, hardening, infrastructure, or other behavior. Earlier prevention also turned merely noticing an optional idea or routinely invoking a reviewed tool into an exhaustive interview. | Implement every detail in the agreed scope or keep the exact gap active in the project's authoritative completion ledger; never trade completeness for speed. Treat a need as in scope only when it is traceable to the request, acceptance criteria, a recorded decision, a user-confirmed assumption, current-system evidence, or the minimum implementation necessary for the requested behavior to work end to end. Before implementing any agent-proposed addition outside that boundary, including a small edge-case policy, obtain explicit approval. Keep the proposal and recommendation concise and make decision detail proportional to impact. Merely noticing and declining an optional idea, making a routine low-level implementation choice, or invoking one reviewed scope-preserving tool does not require an expansion interview. | Require the completeness/expansion distinction, evidence-backed in-scope boundary, approval-before-any-planned-addition rule, proportional-question contract, and no-action/routine-use false-positive guards in universal policy. Add must-catch fixtures for a small unrequested edge-case flow and a hypothetical need labelled credible, plus passing fixtures for necessary end-to-end implementation and optional ideas the agent does not implement. Reject automatic hypothetical hardening, disposable-test-data preservation, and every silent unrequested addition. |
| UIL-AGENT-WORKFLOW-006 | Agent-controlled context, tool selection, and tool output | Agents repeatedly loaded broad unchanged rules, unrelated skills or tools, oversized file ranges, raw logs, full audit reports, or unchanged images, causing high token use without improving the result. | Load only context and capabilities relevant to the current task, use targeted reads and bounded software-generated receipts, keep complete raw evidence and audit results in cold artifacts, and do not reload unchanged content already available in the live context. Every artifact receipt must identify at least the saved filename. | Measure canonical policy size and startup catalogs, add policy checks for relevance and bounded output, require filename-bearing artifact receipts, and distinguish host-injected overhead from repository-controlled behavior. |
| UIL-AGENT-WORKFLOW-007 | Cross-runtime subagent effort selection | Agent workflows named only an internal effort value, obscuring that the runtime UI exposed the same setting under a different label and risking inherited high-effort context. | Name both values—Codex selector `Light`, runtime `low`—validate the selected runtime/model, and use an isolated worker context; if runtime `low` is genuinely unsupported, use the workflow's disclosed manual fallback instead of an invalid spawn or inherited parent transcript. | Require context-light forks with complete prompts, exact label/value wording, filename-bearing artifact-first worker receipts, and fixtures that reject missing mappings or inherited-context instructions. |
| UIL-AGENT-WORKFLOW-008 | Heavy repository-audit skill activation | Full-repository implementation, test-coverage, and implemented-UI audits could enter context through broad implicit matching even when the user had not deliberately requested their expensive exhaustive workflows. | `full-repo-audit`, `full-repo-test-coverage-audit`, and `ui-implementation-audit` require deliberate direct skill invocation; ordinary implementation, UI work, review, testing, visual checking, or gap-finding requests must not activate them implicitly. For `ui-implementation-audit`, the explicit commands are `$ui-implementation-audit` in Codex and `/ui-implementation-audit` in Claude Code. | Set `policy.allow_implicit_invocation: false` in all three Codex metadata files; set Claude Code's native `disable-model-invocation: true` for the scoped `ui-implementation-audit` correction; state the explicit-only gate in its skill contract; and validate both native gates plus the explicit Codex entry prompt. |
| UIL-AGENT-WORKFLOW-009 | Deterministic audit and verifier CLIs | Context isolation depended on the agent remembering an optional quiet/receipt flag, so a valid invocation could still print a complete audit report into model context. | Software owns artifact creation and context-safe output: a normal agent-facing verifier invocation writes complete results to deterministic files and emits only a bounded receipt naming those files; printing a full report requires an explicit human-only opt-in. | Exercise clean, finding, coverage-failure, and setup-failure paths; prove artifacts contain full evidence, default stdout is one bounded receipt, and only the explicit human-output flag prints the report. |
| UIL-AGENT-WORKFLOW-010 | Multi-instance hook installation, activation, and verification | The workflow first required serial clients and Terminal commands, then used a hidden short deadline, lost failure visibility after reboot drift, treated a durable remote app-server like a client, sent the user to SSH, stripped the system path Codex needs for `ps`, mistook a responsive legacy socket with no backend for managed native-stop capability, bound naturally churning task helpers as daemon-lifecycle members, treated expected post-stop managed-daemon teardown lag as an external relaunch, rejected Codex's own trusted-hook state when the host inserted it before a managed-block end marker, and used a synthetic legacy-stop fixture that made every helper disappear when only the daemon was signalled even though the real code-mode host kept the daemon's graceful stop pending. | Give each reviewed Codex home opaque attribution and a recorder-owned one-shot handoff. Bind the proxy, daemon, executable, home, versions, lifecycle backend, required bootstrap features, and only helpers proven to own host-loaded state and to exit with the daemon. Never bind a volatile per-task helper merely because it is same-user or daemon-parented. After native stop, let software own a bounded quiescence wait: an expected exiting process may settle, while a persistent reopened client still fails closed. During activation, accept host-displaced content inside the managed marker only when the recorder payload prefix remains byte-exact, the displaced semantic content begins with a different TOML table, and it contains no OTel definition; keep every managed OTel edit fail-closed. A nonempty backend permits native stop with only the fixed platform path. A Linux legacy server may transition only by gracefully retiring each exact bound host helper before the exact daemon, using pidfd-bound `SIGTERM` throughout, never a bare PID or `SIGKILL`, followed by Codex bootstrap with explicit features and proof of a real backend. Normal users only approve, close/reopen the client once, review host trust, and exercise a fresh task; SSH and Terminal remain recovery-only. | Test interleaved target attribution; realistic managed and legacy daemon/proxy/host-helper topology in which a helper remains until individually signalled and the daemon remains until helpers exit; naturally churning task-helper exclusion; expected post-stop teardown followed by quiescence; persistent client relaunch; real `[hooks.state]` tables inserted before the managed end marker; byte-exact OTel ownership and competing/edited OTel rejection; explicit backend and `code_mode_host`; missing-backend must-catch behavior; exact helper-before-daemon pidfd `SIGTERM`; native bootstrap/stop argv and fixed path; inherited-path rejection; failure, timeout, drift, PID reuse, host relaunch, reboot, crash, collision, rollback, receipt privacy, unrelated-process preservation, and normal-path rejection of SSH/Terminal instructions. |
| UIL-AGENT-WORKFLOW-011 | `user-journey-docs-audit` activation | A greenfield request to critique a domain idea, discuss requirements, and write a specification was treated as a request to audit an existing documentation set because both tasks mentioned product intent, UI, and pre-implementation decisions. | Invoke the skill only when existing product or journey documentation is the audit target and the user requests a documentation-completeness or UI-readiness assessment. Do not activate it for brainstorming, domain or data modeling, database/system specification, ordinary requirements discussion, or co-writing a new specification; “do not start coding,” “critique,” and “roast” are not audit signals by themselves. | Put the complete positive and negative trigger boundary in selector-visible frontmatter, stop before inventory or interview when the applicability gate fails, mirror the boundary in user-facing metadata and README guidance, and test realistic must-call and must-not-call prompts including the reported numbering-system request. |
| UIL-AGENT-WORKFLOW-012 | In-scope local preview, browser QA, and development-runtime coordination in any repository | Agents repeatedly asked for explicit chat authorization before using Playwright or the configured DevCoordinator even though the user wanted those routine tools used autonomously, delaying implementation and verification. | Treat the user's instruction as standing permission to invoke browser automation directly and use the configured development coordinator for in-scope local runtime work in any repository without a separate chat approval. The permission does not expand scope or authorize destructive, production, credential, trust-bypass, or otherwise separately gated actions. | Require the standing-permission boundary in universal policy; reject direct permission questions, stated approval needs, target-first prompts, and ask-before-use phrasing for both tool families; preserve false-positive guards for material scope expansion, production mutation, destructive work, credentials, security gates, installation, and host-owned approval prompts. |
| UIL-AGENT-WORKFLOW-013 | Continuous delivery-efficiency measurement | Activation was presented through a short-lived watch that could expire even while the recorder remained healthy, recorded provider usage stayed unattributed despite explicit phase declarations, raw repository and task IDs were not human-readable without an optional external Coordinator, and synthetic tests passed even though real desktop turns separated declarations from provider counters. This made an always-on measurement system look temporary and prevented useful planning, implementation, testing, deployment, and reporting analysis. | Activation is persistent verified state for the currently configured target, not a user-triggered watch. The per-account recorder is independently usable: it provides bounded readable repository and task views from private local identity metadata and never requires a Coordinator. Exact task-bound provider counters use the configured runtime's authoritative source, including a strictly allowlisted local fallback when exported telemetry is absent; explicit non-overlapping phase declarations classify the matching usage without estimation or cross-task timing guesses, and the host closes a final reporting phase only after delivery usage is captured. Keep per-account stores separate, make Coordinator projection optional, and identify recurring high-cost patterns that are candidates for deterministic automation. | Prove persistent activation survives process and session restart but invalidates for a changed target; exercise real lifecycle order—task start, model counter written, tool hook, phase change, terminal declaration, final counter, stop, automatic phase close—and concurrent sessions with mismatched IDs. Require exact task joins, deduplication between primary and fallback counter sources, truthful unknowns outside a declaration, private repository labels without retained paths, readable active/completed task views, account isolation, and fully functional reports with Coordinator absent or failing. Capability-gated projection remains idempotent; summaries preserve native token categories and provenance; automation suggestions require repeated comparable evidence and false-positive guards. |
| UIL-AGENT-WORKFLOW-014 | Completion-ledger entries and incomplete-work handoffs | Completion ledgers contained implementation jargon, identifiers, and low-level plumbing descriptions without first saying what users can or cannot do, why the gap matters, or where development is going. The stored state was technically populated but unreadable as a progress view. | Write every ledger field for a non-specialist reader first: name the incomplete outcome in plain language, state the present user or product impact and whether it blocks readiness, describe the next result or unblock condition, and explain the observable proof that will close it. Technical detail, affected paths, identifiers, and test names may follow that explanation but never replace it; raw logs stay in cold artifacts. When reporting progress, summarize the ledger's direction, current capabilities, and blockers in the same plain language. | Require a reader-first completion-ledger contract in universal policy and repository guidance for both Markdown and software-owned database modes. Add semantic policy fixtures that reject technical-only explanations or implementation identifiers as substitutes for user impact and accept concise plain-language summaries followed by useful technical detail. Review request-related active ledger records and handoffs against the contract before readiness. |
